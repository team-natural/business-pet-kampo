# 02-operations-handbook.md — 運用ハンドブック

## このセクションの目的

リリース後の日常運用に **最低限必要な実作業** を 1 冊に統合する：サポート窓口（§1）、インシデント初動（§2）、リリース・ロールバック実作業（§3）、バックアップ・データ保持（§4）。

技術選定（インフラ・ツール名）は DEV-01 §1 / §2 を正本とし、本書では原則「基盤」「オブジェクトストレージ」等の一般名で記述する。ロールバックの判断基準は DEV-08 §5、SLA 数値は OPS-01 §3 が正本であり、本書は実作業手順のみを持つ。

## 0-H. ハイブリッド編集ガイド（要点）

- 推奨モード: Hybrid（AI 下書き + Tech Lead / サポート担当 確定）
- 人間確認必須: 実際に守れる受付時間、体制人数で回るエスカレーション、ロールバック手順の実行可能性

---

## 0. 対応時間の原則（全章共通）

- 障害対応・サポート対応は **業務時間内（平日 9:00〜18:00）のベストエフォート** とする。
- 時間外・休日は自動アラート（監視・エラー通知）の記録のみを行い、**対応は翌営業日** とする。24/7 の人的オンコールは置かない。
- 体制は **Tech Lead / PdM / サポート担当** の少数ロール（兼務前提）で構成する。

## 1. サポート窓口・エスカレーション

### 1-1. 提供範囲

- 対象：新規取引申請の審査状況問い合わせ、アカウントサポート（パスワードリセット等）、発注・決済サポート（発注内容確認・入金確認状況）、商品に関する問い合わせ、障害受付
- 範囲外：個々の商品の医療的な効果に関する相談（INTAKE §7 表現規制、獣医師へ相談するよう案内）、会計・税務相談

### 1-2. 受付チャネル

| チャネル | 受付時間 | 対象 |
| --- | --- | --- |
| お問い合わせフォーム（PRD-04 §3-1 SCR-30）| 24h 受付、平日 9:00〜18:00 に返信 | 全利用者 |
| メール | 24h 受付、平日 9:00〜18:00 に返信 | 承認済み取引先 |
| よくある質問（FAQ）| 24h（自己解決）| 全利用者 |

一次応答時間 SLA は **OPS-01 §3-3 を正本** とし、本書では再掲しない。電話受付は提供しない。

> FAQ の**加筆・修正は運営側では行えない**（管理画面を持たないページ直書き — DEV-06 §1-1）。「この質問を FAQ に追加したい」という要望は §3-6 の開発タスクとして扱う。

### 1-3. エスカレーション

一次対応（サポート担当）で解決しない問い合わせは以下へエスカレーションする。

| 条件 | エスカレーション先 |
| --- | --- |
| 技術的原因の調査が必要（バグ・障害級疑い）| Tech Lead → 障害級は §2 のインシデント初動へ |
| 新規取引申請の審査差し戻し・否認理由の再確認 | PdM（審査基準の確認）|
| 決済トラブル（重複請求・入金確認の齟齬）| PdM + Tech Lead |
| データ消失の疑い | Tech Lead（§4 のバックアップから調査）|
| 個人情報インシデント | Tech Lead 主導で DEV-02 §11 のフローへ |
| FAQ・利用規約・診断ルールの文面修正依頼 | Tech Lead（§3-6 の開発タスクとして受ける。規約文面は PdM + 法務も経由 — OPS-01 §5-2）|
| 法的クレーム・著作権侵害申立（他社商品画像の無断掲載疑い等）| PdM（必要に応じて弁護士へ相談）|

## 2. インシデント初動

### 2-1. 重大度定義と解決目安

| Severity | 定義 | 例 | 解決目安 |
| --- | --- | --- | --- |
| **P0（Critical）** | サービス全体停止、データ漏洩、決済重複 | アプリ全停止、卸価格の非承認者への漏洩、二重決済 | **当日中** |
| **P1（High）** | 主要機能の停止または重大なデータ問題 | 発注・決済不可、新規取引申請フォーム全停止 | **1 営業日以内** |
| **P2（Medium）** | 一部機能の停止または特定取引先への影響 | 特定取引先のログイン不能、商品画像の一部取得不能 | **3 営業日以内** |
| **P3（Low）** | UI 不具合、軽微な性能劣化 | 一部画面の表示崩れ | **次回リリース** |

> 上記は運用目安であり、正式な SLA ではない（SLA は OPS-01 §3）。時間外に検知したものは §0 の原則により翌営業日起算とする。

### 2-2. 障害に含めないもの

| 除外区分 | 対応方針 |
| --- | --- |
| 取引先起因の誤操作・誤入力（配送先の入力ミス等）| 操作ガイドを案内、必要に応じデータ修正を支援 |
| 契約範囲外の機能実装依頼 | OPS-01 §2 の契約範囲を説明し、要望として記録 |
| 外部サービス起因のみの問題（決済・DNS 等）| 外部ステータスページを案内し復旧待ち（ベストエフォート）|
| 動作保証外のブラウザ・OS での不具合 | 対応環境一覧を案内。対応環境でも再現する場合は障害扱い |

### 2-3. 初動フロー

```
1) 検知（監視アラート / ユーザー通報）
2) Tech Lead が重大度判定（P0〜P3）・対応チャネルで状況共有開始
3) P0/P1: 復旧最優先で原因究明・暫定対応（ロールバック判断は DEV-08 §5、実作業は §3-3）
   P2: 担当者アサインの上、通常対応
   P3: Issue 化して次回リリースに組み込み
4) 復旧確認 → 顧客通知（§2-4）
5) P0/P1 は簡易ふりかえりを GOV-01 に記録（原因・影響・再発防止策）
```

### 2-4. 顧客通知基準

| Severity | 通知タイミング | チャネル | 対象 |
| --- | --- | --- | --- |
| P0 | 重大度判定後、速やかに（30 分以内目安）| マイページお知らせ + メール | 全承認済み取引先 |
| P1 | 判定後 1 時間以内目安 | マイページお知らせ + 影響取引先へメール | 影響取引先 |
| P2 | 復旧見込み判明時 | マイページお知らせ | 影響取引先 |
| P3 | 通知不要（次回リリースノートに記載）| — | — |

時間外検知の場合の通知は翌営業日とする（§0）。

> 障害の告知に使う「マイページお知らせ」は D1 の `news`（管理画面から即時投稿可 — DEV-06 §1-1）である。**アプリが落ちている P0 では管理画面も落ちている可能性がある**ため、P0 の一報はメールを主とし、お知らせは復旧後に記録として残す。

通知文面テンプレート（初報。復旧報も同形式で【影響時間】【原因】【対応】を追記）：

```
件名: 【お詫び】サービスの一時的な障害について

現在、以下の障害が発生しております。

【発生時刻】 YYYY/MM/DD HH:MM
【影響範囲】 （例：ログイン・発注機能 / 一部機能のみ）
【現状】 原因調査中 / 暫定対応中 / 復旧作業中
【復旧見込み】 （例：現時点では未定 / HH:MM 頃を目標）

進捗は随時マイページお知らせでお知らせいたします。

<サービス名>運営チーム
```

### 2-5. 個人情報インシデント

内部報告・行政報告・本人通知の期限とフローは **DEV-02 §11 を正本** とする。検知した時点で他の作業に優先して同フローを開始する。

## 3. リリース・ロールバック実作業

デプロイ基盤・環境構成・CI/CD・デプロイゲートは DEV-08 §1〜§6 を参照。本章は Workers Builds によるデプロイ実行を前提に、人間が行う確認作業とロールバック実作業のみを定義する。

### 3-1. 通常リリース手順

```
1) リリース対象 PR を集約し、CI 全 Pass を確認（内容は DEV-08 §3-1。
   pnpm db:generate → pnpm check → E2E → build の順で走る）
2) リリースノート（GitHub Release Draft）を作成
3) main へ PR 経由でマージ → Cloudflare Workers Builds が deploy を実行（DEV-08 §3-2）。
   Cloudflare Workers のデプロイはエッジでアトミックに切り替わるため無停止
4) ヘルスチェック（全エンドポイントの定義は DEV-08 §9。両アプリそれぞれに実行する）
   curl https://{PUBLIC_URL}/api/v1/health
   curl https://{PUBLIC_URL}/api/v1/health/db
   curl https://{ADMIN_URL}/api/v1/health
   curl https://{ADMIN_URL}/api/v1/health/kv     # KV 採用済み（DEV-01 §1）
   # /health/queue は不要（Queues 不採用 — DEV-01 §1）
5) スモークテスト（§3-2）
6) デプロイ直後はエラー率・メトリクスを Cloudflare ダッシュボード（Workers Logs / Analytics）
   または `wrangler tail` のライブログで監視
   （ロールバック発動条件は DEV-08 §5 — 本書では再掲しない）
7) 異常なし → リリース完了報告 + GitHub Release を Publish
```

マイグレーションを含むリリースは、事前に staging で dry-run し、無停止可能なこと・前方互換であること（DEV-08 §4、D1 マイグレーションは forward-only）を確認してからマージする。

**2 つの Worker は同時に切り替わらない**（DEV-08 §3-2）。スキーマ変更を伴うリリースでは admin 側が先に出るため、手順 4〜5 は両アプリに対して行う。

初回リリース前の事前確認は **DEV-08 §7-3 の検証完了チェックリスト** を使用する（本書には持たない）。

### 3-2. リリース後スモークテスト

```
[ ] トップページ・商品一覧・商品詳細の正常表示（エラー・レイアウト崩れなし）
[ ] 商品詳細で卸価格が「未ログインでは出ない / ログイン後は出る」ことを確認
[ ] 商品選び診断が最後まで進み、推奨商品が表示される（ハイドレーション確認）
[ ] FAQ・利用規約・プライバシーポリシー・特商法表示の各ページが 200 で表示される
[ ] ログイン / ログアウト動作（メール・LINE・Google・Facebook）
[ ] 新規取引申請フォームの送信〜完了画面表示
[ ] カート追加 〜 発注確定 〜 発注完了画面表示（テスト取引先で）
[ ] 決済 Webhook 受信確認（stripe-cli 等でテストイベント送信）
[ ] メール送信確認（申請受付・発注確認等をテスト送信で受信確認）
[ ] 管理画面のログイン 〜 ダッシュボード表示
[ ] HTTPS 有効確認（証明書エラーなし）
```

### 3-3. ロールバック実作業

判断基準は **DEV-08 §5 が正本**。該当したら以下を実行する（迷ったらロールバックを優先）。

```
1) コードのロールバック：
   Cloudflare ダッシュボード（Workers > Deployments）または
   `wrangler deployments list` で前デプロイメントを確認し、`wrangler rollback` で戻す
   ※ 対象の Worker を間違えないこと（public / admin は別 Worker）
2) マイグレーションを伴う場合：
   - 前方互換マイグレーション → D1 はそのまま（コードのみ戻す）
   - 破壊的マイグレーション → 戻すのではなく、新規マイグレーションで修正
3) データ修正が必要な場合：
   - メンテナンスモード相当の仕組みは未実装（実現方式は KV フラグ +
     各アプリの `src/middleware.ts` での判定で確定。実装は必要になった時点で行う）
   - データ修正自体は `wrangler d1 execute --command '...'`（または管理画面経由）で実行し、
     修正内容は必ず監査ログに記録する
4) ロールバック実施を §2 のインシデントとして記録（P0/P1 相当なら GOV-01 にふりかえり）
```

### 3-4. 緊急リリース（Hotfix）

```
1) main から hotfix ブランチを作成（hotfix/短い説明）
2) 修正 + 関連テスト・静的解析・フォーマッタを通す
3) PR 作成 → 承認は Tech Lead（兼務可）。P0 対応時は事後レビュー可
4) マージ → デプロイ実行（§3-1 の 3）→ §3-1 の 4〜7 を実施
5) 修正を開発ブランチにも反映
```

### 3-5. 計画停止（メンテナンスモード）

停止を伴う作業（大規模マイグレーション等）は、OPS-01 §3-4 の通知条件（7 日前通知・月 1 回まで）を満たした上で実施する。メンテナンスモードの実現方式は KV フラグ + 各アプリの `src/middleware.ts` 判定で確定（§3-3 参照）。作業完了後に §3-1 の 4〜5 を実施する。

### 3-6. コンテンツ更新（診断ルール・FAQ・法務ページ）

公開コンテンツの一部は D1 ではなくリポジトリで管理しており（DEV-06 §1-1）、**更新にデプロイを伴う**。運営から依頼を受けたときの扱いを明確にしておく。

| 依頼内容 | 更新者 | 作業単位 |
| --- | --- | --- |
| 商品・メーカー・ブランド・カテゴリー・お知らせの追加/修正 | 運営（管理画面）| 即時。開発の関与なし |
| FAQ の加筆・修正 | 開発者 | PR → レビュー → マージ → デプロイ → 表示確認 |
| 商品選び診断の質問・推奨商品の調整 | 開発者 | 同上。加えて推奨商品の slug が実在する公開商品を指すか確認（DEV-03 §3-5）|
| 利用規約・プライバシーポリシー・特商法表示の修正 | 開発者 | 同上 + **法務レビュー** + **バージョン定数の更新**（OPS-01 §5-2）|

- 依頼は「運用作業」ではなく **開発タスク** として受け、リードタイムは PRD-03 §6-3 のデプロイ頻度に従う
- 文面の修正だけでも §3-1 の手順（CI → デプロイ → 確認）を省略しない
- **診断ルールを頻繁に調整したいという要望が続く場合**は、Content Collections から D1 + 管理画面へ移す判断を GOV-02 TBD-09 / TBD-20 で再評価する（GOV-01 D-015 の再評価条件）

## 4. バックアップ・データ保持

### 4-1. バックアップ方針

DB は Cloudflare D1（Cloudflare マネージドの SQLite 互換データベース）を使用する。D1 には **Time Travel（ポイントインタイムリカバリ）が常時有効**で、分単位の任意時点へ追加コストなしで復元できる（保持: Workers Paid 30 日 / Free 7 日）。これを第一の復旧手段とし、保持期間を超える長期保管・オフサイト保管が必要な場合のみ `wrangler d1 export` による日次エクスポートを併用する。

| 対象 | 方式 | 頻度 / 保持 |
| --- | --- | --- |
| DB（Cloudflare D1）| Time Travel（常時有効・PITR。復元は `wrangler d1 time-travel restore`）+ 長期保管が必要な場合のみ `wrangler d1 export` 併用 | Time Travel: 30 日（Paid）/ 7 日（Free）。export 併用時: 日次 / 30 日超 |
| オブジェクトストレージ（R2、商品画像等）| 別バケットへの複製 | 日次 / 30 日 |
| 監査ログ | 削除不可・永続保持（PRD-02 §8）。D1 のバックアップに含めた上で長期保管先を確保 | 永続 |
| 診断ルール・FAQ・法務ページの文面 | Git リポジトリ（バックアップ対象外 — リモートリポジトリが正本）| 永続 |

> D1 を過去時点へ復元すると、**その時点以降に運営が管理画面から登録した商品・お知らせも消える**。復元は最後の手段とし、範囲を限定できる場合は個別のデータ修正（§3-3 の 3）を優先する。

### 4-2. RTO / RPO 目標（軽量版）

| 区分 | RTO（復旧目標）| RPO（許容データ損失）|
| --- | --- | --- |
| DB 全損 | 1 営業日 | 24 時間（バックアップ間隔）|
| オブジェクトストレージ部分損失 | 1 営業日 | 24 時間 |
| 監査ログ | — | 0（永続化必須）|

### 4-3. データ保管期限の自動削除バッチ

PRD-02 §8 のデータライフサイクルに準拠し、日次バッチで自動削除する（個人情報保護対応）。バッチの起動方法は Cloudflare Cron Triggers（DEV-01 §2。`wrangler.jsonc` の `triggers.crons` で定義し、対応する Scheduled Worker 内で以下の処理を実行する）。

```ts
// 毎日 03:00 JST 実行（Cron Triggers — DEV-01 §2）
purgeExpiredApplications(); // 否認・取消から 1 年経過した申請を物理削除（DEV-07 §10）
purgeTerminatedOrganizations(); // 取引終了から 1 年経過した取引先を物理削除
purgeExpiredInquiries(); // 対応完了から 1 年経過した問い合わせを物理削除
purgeExpiredSessions(); // 有効期限切れの admin_sessions / member_sessions を削除
rotateLogs(); // 操作ログの保持期間超過分を削除
```

- 期限到達前にユーザーへ段階通知する（取引終了後 1 年の保管期限に対する事前通知。90 日前メール → 30 日前再通知 → 7 日前最終通知 → 削除実行後に完了通知）
- 自動削除は必ず監査ログに記録する（システム起点のため causer は NULL のまま、event: `data.purged`、発生源は properties で示す — DEV-05 §9-1）
- 取引終了時のデータ保持・エクスポート条件は OPS-01 §4-3 と整合させる
- 発注・決済履歴（会計データ）は自動削除の対象外とする（DEV-02 §8-1 参照）

## 5. リリース後に育てる項目

以下は本書ではあえて定義しない。**運用開始後に必要になった時点で GOV-02 に起票して整備する**。

| 項目 | 起票の目安 |
| --- | --- |
| 運用 KPI の目標値・計測（応答時間 p90、解決率、CSAT 等）| 問い合わせ量が体感で追えなくなったら |
| チケット管理ツールの導入・移行 | メール + 手動管理で漏れが出始めたら |
| FAQ の管理画面化（D1 + ADM 画面の追加）| 運営が自分で FAQ を更新したい要望が続いたら（GOV-02 TBD-20）|
| 診断ルールの管理画面化（D1 + ADM 画面の追加）| 運営がルールを頻繁に調整したい要望が出たら（GOV-02 TBD-09 / TBD-20、§3-6）|
| ステータスページ（外部公開の稼働状況）| 障害時の問い合わせ集中が負担になったら |
| インシデント対応訓練・バックアップリストア訓練 | 初回の実インシデント対応後 |
