# 03-functional-requirements.md — 機能要件定義

## このセクションの目的

提供すべき機能、MVP スコープ、受け入れ条件、非機能要件を定義する。**本プロジェクトはチャット・AI 機能を採用しないため（PRD-05 参照）、チャット・AI 関連の機能グループは本書に含めない。**

## 0-H. ハイブリッド編集ガイド（要点）

- 推奨モード: Hybrid（AI 草案 + PdM 主導で確定）
- 人間確認必須: MVP 判断、優先度、非機能数値、受入条件の妥当性

### FG-06 （欠番）管理画面：商品・メーカー・ブランド管理

**本グループは存在しない**（GOV-01 D-017）。商品・メーカー・ブランド・分類・商品画像はすべて開発者が `packages/content` と静的アセットで管理し、管理画面を持たない。旧 F-06-01〜F-06-10 に対応する運用は以下に置き換わる。

| 旧機能 ID | 旧機能名 | 置き換え後 |
| --- | --- | --- |
| F-06-01 | 商品追加・編集 | `packages/content/products/*.md` の追加・編集（コミット + デプロイ）|
| F-06-02 | 商品公開・非公開切り替え | frontmatter の `draft: true` |
| F-06-03 | 取扱開始・取扱終了切り替え | frontmatter の `discontinued: true`。**ファイルを削除しない** — 削除してもスナップショットにより過去の注文は壊れないが、再開時に書き直しになる |
| F-06-04 | 商品画像管理 | `apps/public/src/assets/img/` へのコミット（GOV-01 D-020）|
| F-06-05 | 一般公開情報・卸売情報の分離管理 | frontmatter 上は同一ファイル。**表示側で分離する**（卸価格はセッション検証後のみ描画 — F-03-03）|
| F-06-06 | 表示順変更 | frontmatter の `order` |
| F-06-07〜F-06-08 | メーカー・ブランド管理 | `packages/content/{manufacturers,brands}/*.md` |
| F-06-09〜F-06-10 | カテゴリー・気になる点管理 | `apps/public/src/lib/catalog.ts` の定数（GOV-01 D-024）|

> 商品の `slug` は注文明細（`order_items.product_slug`）・診断ルール・公開 URL の 3 か所から参照され、**外部キー制約で守られない**。リネームせず、必要な場合は旧 slug からのリダイレクトを追加する（DEV-06 §1-1、DEV-07 §6-0）。

## 3. ユーザーストーリー（主要のみ）

### US-01 新規取引希望事業者の申請

- **As a** ペット関連商品を扱う事業者
- **I want** 商品情報を確認したうえで新規取引を申請したい
- **So that** 卸価格で仕入れができるようになりたい
- 関連 KPI: KPI-02（新規取引申請承認率）
- 関連機能 ID: F-02-01, F-02-02

### US-02 運営管理者の審査業務

- **As a** 運営管理者
- **I want** 申請内容を確認し、必要なら追加確認をしたうえで承認・否認したい
- **So that** 卸価格を非公開に保ちながら適切な取引先だけを迎え入れたい
- 関連 KPI: KPI-03（申請審査リードタイム）
- 関連機能 ID: F-02-03〜F-02-09

### US-03 承認済み取引先の商品選定・発注

- **As a** 承認済み取引先の担当者
- **I want** 専門知識がなくても商品選び診断で自店に合う商品を見つけ、そのままカートに入れて発注したい
- **So that** 発注業務にかかる時間を減らしたい
- 関連 KPI: KPI-04（月間発注件数）, KPI-07（診断利用率）
- 関連機能 ID: F-03-10, F-04-01〜F-04-11

### US-04 承認済み取引先の発注履歴確認

- **As a** 承認済み取引先の担当者
- **I want** 過去の発注内容・ステータスをいつでも確認したい
- **So that** 経理処理や再発注の判断に使いたい
- 関連機能 ID: F-05-05, F-05-06

### US-05 運営管理者の受注・入金管理

- **As a** 運営管理者
- **I want** 受注一覧から決済状況・入金状況を確認し、ステータスを更新したい
- **So that** 出荷・請求業務を滞りなく進めたい
- 関連機能 ID: F-08-01〜F-08-07

## 4. MVP スコープ定義

### 4-1. MVP 含有判断ルール

- MVP `○` = 実装対象（優先度 High / Medium は**重要度**であり、着手順ではない）
- **着手順の正本は 00_DEV_GUIDE §3-3a の実装ステージ S1〜S16**（業務ライフサイクルの依存順 — GOV-01 D-032）。優先度順に着手すると、先行機能が生成するデータ（Organization / Member 等）が存在せず着手できない
- High 優先度で MVP `△` は MVP 検証後に追加実装
- Medium / Low はベータ後の改善サイクルで判断

### 4-2. 含める機能（要約）

- 認証（FG-01: F-01-02 〜 F-01-07。**AdminUser のログインは Cloudflare Access に置き換え** — GOV-01 D-022）
- 新規取引申請・審査（FG-02: 全機能）
- 商品カタログ・検索（FG-03: F-03-01 〜 F-03-09。**診断 F-03-10 / F-03-11 は除外**）
- カート・発注（FG-04: 全機能）
- マイページ（FG-05: 全機能）
- 管理画面：新規取引申請・取引先管理（FG-07: 全機能。F-07-10 は参照表示のみ）
- 管理画面：受注管理（FG-08: 全機能）
- お知らせ・お問い合わせ（FG-09: F-09-01・F-09-03 〜 F-09-06。**F-09-02 は廃止**）
- 通知（FG-10: 全機能）
- 管理操作履歴（FG-11: F-11-01）
- 退会・取引終了（FG-12: 全機能）

> **FG-06（商品・メーカー・ブランド管理）はグループごと MVP から消えた**（GOV-01 D-017）。管理画面は 25 画面から 12 画面に、D1 テーブルは 24 から 17 に減っている。工数前提を引く際はこの差分を織り込むこと。

### 4-3. 除外項目と理由

| 除外機能 | 理由 | 将来再評価タイミング |
| --- | --- | --- |

## 5. 受け入れ条件フォーマット

Given / When / Then の 3 要素で記述する。

```
Given <前提条件>
When <ユーザー操作>
Then <期待結果>
And <追加の期待結果>
```

例：

```
Given 承認済み取引先の担当者（Member）がログインしている
When 商品詳細から数量を指定して「カートに追加」する
Then カート内に商品が追加され、卸単価・小計が表示される
And 未承認の利用者が同じ操作をした場合はログイン/新規取引申請へ案内される
```

## 6. 非機能要件

### 6-1. 性能・可用性

数値目標は本書では再掲せず、以下の正本に従う（同じ数値を複数文書で持たない）。

| 区分 | 数値目標の正本 | 検証方法の正本 |
| --- | --- | --- |
| 性能（画面描画 / API / 検索・診断応答の p95）| DEV-01 §6（非機能要件）| DEV-03 §3（テスト戦略）・§7（KPI 接続）|
| 可用性（月間稼働率）| PRD-02 §5-2（公開側と会員側/管理側で目標が異なる点に注意）| OPS-02（死活監視・デプロイゲート）|
| スケール（同時接続）| DEV-01 §6 | DEV-08 §7（検証完了ゲートの負荷テスト）|

> 診断の応答時間は D1 の読み取りを伴わない（ルールはビルド時に解決される）ため、商品検索より有利な条件になる。ボトルネックは推奨商品の商品情報取得（D1）側に現れる（PRD-02 §1-4）。

### 6-2. セキュリティ

詳細は DEV-02 参照。

- 認証: AdminUser・Member ともに D1 裏付けのセッション認証。Member のみ OAuth（Arctic）を追加で提供する（DEV-01 §2）
- ロール: AdminUser（ロール区分なし）+ Member（`client_user`、Organization に所属）の最小構成（PRD-01 §1-2 / DEV-02 §2）
- データ分離: 発注関連データのみ `organization_id` スコープ強制（PRD-02 §2）
- 監査ログ: 重要操作を監査ログへ記録（記録先は自前の D1 テーブル。DEV-01 §2、必須記録操作は DEV-05 §9-1）

### 6-3. 保守性

- デプロイ頻度: 週 1 回以上を安全に実施可能
- 主要修正のリードタイム: 1 日以内
- バージョン更新: セキュリティパッチは重大度に応じて適用（運用は OPS-02）
- **公開コンテンツの更新はすべてデプロイを伴う**（商品・お知らせ・診断ルール・FAQ・法務ページ。GOV-01 D-017・D-018）。上記のデプロイ頻度・リードタイムがそのままコンテンツ更新のリードタイムになる（OPS-02 §運用作業）。**臨時休業や出荷遅延の告知もこのリードタイムに従う** — 即時に出せないことを運用側と合意しておくこと
