# 03-functional-requirements.md — 機能要件定義

## このセクションの目的

提供すべき機能、MVP スコープ、受け入れ条件、非機能要件を定義する。**本プロジェクトはチャット・AI 機能を採用しないため（PRD-05 参照）、チャット・AI 関連の機能グループは本書に含めない。**

## 0-H. ハイブリッド編集ガイド（要点）

- 推奨モード: Hybrid（AI 草案 + PdM 主導で確定）
- 人間確認必須: MVP 判断、優先度、非機能数値、受入条件の妥当性

## 3. ユーザーストーリー（主要のみ）

### US-01 新規取引希望事業者の申請

- **As a** ペット関連商品を扱う事業者
- **I want** 商品情報を確認したうえで新規取引を申請したい
- **So that** 卸価格で仕入れができるようになりたい
- 関連 KPI: KPI-02（新規取引申請承認率）
- 関連機能 ID: F-02-01, F-02-02

### US-02 運営管理者の審査業務

- **As a** 運営管理者
- **I want** 申請内容を確認し、必要なら追加確認をしたうえで承認・否認したい
- **So that** 卸価格を非公開に保ちながら適切な取引先だけを迎え入れたい
- 関連 KPI: KPI-03（申請審査リードタイム）
- 関連機能 ID: F-02-03〜F-02-09

### US-03 承認済み取引先の商品選定・発注

- **As a** 承認済み取引先の担当者
- **I want** 専門知識がなくても商品選び診断で自店に合う商品を見つけ、そのままカートに入れて発注したい
- **So that** 発注業務にかかる時間を減らしたい
- 関連 KPI: KPI-04（月間発注件数）, KPI-07（診断利用率）
- 関連機能 ID: F-03-10, F-04-01〜F-04-11

### US-04 承認済み取引先の発注履歴確認

- **As a** 承認済み取引先の担当者
- **I want** 過去の発注内容・ステータスをいつでも確認したい
- **So that** 経理処理や再発注の判断に使いたい
- 関連機能 ID: F-05-05, F-05-06

### US-05 運営管理者の受注・入金管理

- **As a** 運営管理者
- **I want** 受注一覧から決済状況・入金状況を確認し、ステータスを更新したい
- **So that** 出荷・請求業務を滞りなく進めたい
- 関連機能 ID: F-08-01〜F-08-07

## 4. MVP スコープ定義

### 4-1. MVP 含有判断ルール

- MVP `○` = 実装対象（優先度 High / Medium は着手順を表す）
- High 優先度で MVP `△` は MVP 検証後に追加実装
- Medium / Low はベータ後の改善サイクルで判断

### 4-2. 含める機能（要約）

- 認証（FG-01: F-01-01 〜 F-01-07）
- 新規取引申請・審査（FG-02: 全機能）
- 商品カタログ・検索・診断（FG-03: F-03-01 〜 F-03-10）
- カート・発注（FG-04: 全機能）
- マイページ（FG-05: 全機能）
- 管理画面：商品・メーカー・ブランド管理（FG-06: 全機能）
- 管理画面：新規取引申請・取引先管理（FG-07: 全機能）
- 管理画面：受注管理（FG-08: 全機能）
- お知らせ・お問い合わせ（FG-09: 全機能）
- 通知（FG-10: 全機能）
- 管理操作履歴（FG-11: F-11-01）
- 退会・取引終了（FG-12: 全機能）

### 4-3. 除外項目と理由

| 除外機能 | 理由 | 将来再評価タイミング |
| --- | --- | --- |
| 複数ログイン方法の紐付け（F-01-08）| MVP では 1 Member 1 ログイン方法で開始し、運用負荷を見て拡張 | MVP 検証後 |
| Uchinoko 専用診断とブランド横断診断の切替（F-03-11）| 診断ルールの詳細設計が未確定（GOV-02 TBD-09）| 診断ルール確定後 |
| 診断ルールの管理画面（診断セット・質問・選択肢・推奨商品の CRUD）| ルールは Content Collections で開発者が更新する（GOV-01 D-015）。テーブルと管理画面を持たないことで MVP から 4 テーブル + 管理画面 1 系統を削減した | 運営自身がルールを調整したい要望が出た時点（GOV-02 TBD-09 / TBD-20）|
| FAQ・法務ページの管理画面 | ページ直書きで開発者が更新する（GOV-01 D-016）| GOV-02 TBD-20 |
| 在庫管理・取り寄せ・メーカー直送 | 在庫管理は不要と確定（GOV-01 D-011）| 需要が明確になった時点で再検討 |
| 掛売り（信用取引）| 提供しないことが確定（GOV-01 D-010）。全取引先がカード決済・銀行振込のいずれかで支払う | 対象外（再評価予定なし）|
| チャット・AI 機能 | INTAKE に要望なし。診断はルールベースで十分（PRD-05 参照）| 需要が明確になった時点 |

## 5. 受け入れ条件フォーマット

Given / When / Then の 3 要素で記述する。

```
Given <前提条件>
When <ユーザー操作>
Then <期待結果>
And <追加の期待結果>
```

例：

```
Given 承認済み取引先の担当者（Member）がログインしている
When 商品詳細から数量を指定して「カートに追加」する
Then カート内に商品が追加され、卸単価・小計が表示される
And 未承認の利用者が同じ操作をした場合はログイン/新規取引申請へ案内される
```

## 6. 非機能要件

### 6-1. 性能・可用性

数値目標は本書では再掲せず、以下の正本に従う（同じ数値を複数文書で持たない）。

| 区分 | 数値目標の正本 | 検証方法の正本 |
| --- | --- | --- |
| 性能（画面描画 / API / 検索・診断応答の p95）| DEV-01 §6（非機能要件）| DEV-03 §3（テスト戦略）・§7（KPI 接続）|
| 可用性（月間稼働率）| PRD-02 §5-2（公開側と会員側/管理側で目標が異なる点に注意）| OPS-02（死活監視・デプロイゲート）|
| スケール（同時接続）| DEV-01 §6 | DEV-08 §7（検証完了ゲートの負荷テスト）|

> 診断の応答時間は D1 の読み取りを伴わない（ルールはビルド時に解決される）ため、商品検索より有利な条件になる。ボトルネックは推奨商品の商品情報取得（D1）側に現れる（PRD-02 §1-4）。

### 6-2. セキュリティ

詳細は DEV-02 参照。

- 認証: AdminUser・Member ともに D1 裏付けのセッション認証。Member のみ OAuth（Arctic）を追加で提供する（DEV-01 §2）
- ロール: AdminUser（ロール区分なし）+ Member（`client_user`、Organization に所属）の最小構成（PRD-01 §1-2 / DEV-02 §2）
- データ分離: 発注関連データのみ `organization_id` スコープ強制（PRD-02 §2）
- 監査ログ: 重要操作を監査ログへ記録（記録先は自前の D1 テーブル。DEV-01 §2、必須記録操作は DEV-05 §9-1）

### 6-3. 保守性

- デプロイ頻度: 週 1 回以上を安全に実施可能
- 主要修正のリードタイム: 1 日以内
- バージョン更新: セキュリティパッチは重大度に応じて適用（運用は OPS-02）
- **コンテンツ更新のうち診断ルール・FAQ・法務ページはデプロイを伴う**ため、上記のデプロイ頻度・リードタイムがそのままコンテンツ更新のリードタイムになる（OPS-02 §運用作業）

## 7. 記入時チェックポイント

- 機能ごとに「誰のどんな価値」が説明できるか
- 機能 ID と PRD-04 の画面 ID が対応するか
- MVP に入れない理由が明文化されているか
- 受け入れ条件がテスト可能な文になっているか
- 商品カタログが未承認者にも公開される一方、卸価格・発注操作が承認済み取引先限定になっているか（FG-03/FG-04 の境界確認）
- 診断結果（F-03-10）に卸価格が漏れていないか（PRD-02 §2-3）
- 管理画面機能（FG-06〜FG-08、F-09-02、F-09-06）が D1 のエンティティにのみ対応し、Content Collections・直書きコンテンツに対する CRUD を要求していないか（§1 の注記）
- AdminUser と Member が別系統として記述されているか（FG-01 の対象列を参照）
- チャット・AI 機能を採用していないことが明記され、PRD-05 と整合しているか
- 非機能要件の数値を本書に書いていないか（§6-1 の正本表に従い、DEV-01 §6 / PRD-02 §5-2 を参照する）
