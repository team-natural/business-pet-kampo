# 00_INTAKE.md — 案件ヒアリング正本

## このセクションの目的

本ファイルは、顧客ヒアリング・既存資料・コンサル所感を「生の事実 + 引用 + 仮置きラベル」で集約する **案件入力の正本** です。BIZ-01 以降の仕様書を AI または人間が初稿生成する際の唯一の入力源として参照します。

## 0. 編集ルール

- **書く人**: コンサルタント（または PdM）
- **読む対象**: 後続仕様書を起こす AI、案件参加者
- **AI の編集権限**: 読み取り専用。AI が再構成・要約する場合は別ファイルへ
- **更新の流れ**: 顧客から新事実が出たら、まず本ファイルへ追記。仕様書の修正はその後
- **既存記述は消さない**: 古い前提も取り消し線で残し、いつ何が変わったかを §11 変更履歴で追える形にする
- **発言の引用**: `> 「...」（発言者, 日付）` 形式
- **仮置き表記**: コンサルの推測・補完は末尾に `[Assumed: 根拠 / 確認先]` を付ける
- **開示区分**: front-matter `disclosure: internal-only` を原則とする。顧客開示する場合は別ファイル（`00_INTAKE_customer.md` 等）を作成して共有する

### 4-1. サービスコンセプト

> 「犬・猫向けの漢方、自然由来サプリメント、健康維持関連商品を取り扱う、法人・事業者向けの卸売サイトを提供する。自社ブランドの商品だけでなく、他社メーカー・他社ブランドの商品も取り扱う。」（依頼者, 2026-08-16）

→ コンサル所感: 自社ブランド商品と他社商品を横断的に扱う「マルチブランド卸売カタログ」がコアコンセプト。一般消費者向け販売は明確に対象外（BtoB 専業）。

### 4-2. ターゲットユーザー

> 「新規取引を希望する事業者に対して、商品情報および卸取引に関する情報を公開し、取引申請を受け付ける。運営会社による審査を通過した取引先だけが、卸価格の確認および商品の発注を行える。」（依頼者, 2026-08-16）

→ コンサル所感: 審査制の会員制卸売サイト。商品ページ自体は SEO・新規開拓のため一般公開し、卸価格・発注機能のみを承認済み取引先に限定するゲート構造。`apps/public`（Astro SSR）でログイン状態に応じてリクエストごとに出し分ける（静的生成ではないため技術的な制約はない — DEV-01 §1）。

### 4-3. 差別化ポイント・初期主要商品

> 「初期の主要商品の一つとして「ペット養生 Uchinoko」を取り扱う。参考: https://pet-kampo.natural-ai.workers.dev/ 。Uchinokoはサイト全体のブランド名ではなく、取り扱い商品の一つとして扱う。」（依頼者, 2026-08-16）

→ コンサル所感: 「Uchinoko」は数ある取扱商品・ブランドの一つであり、サイトブランドと商品ブランドを混同しない設計が必要（PRD-01 のユビキタス言語で明確化）。

### 4-4. 技術方針

> 「Astro + Svelte のテンプレートを社内主軸で進めている。LLM は Claude を主に、用途で他も併用」（PdM, 2026-08-18）

→ コンサル所感: 社内標準スタック（Astro SSR + Svelte islands + Cloudflare Workers/D1/R2、00_README §0-1 のパターン A）を採用する。技術選定は DEV-01 を正本とする。AI 機能は任意採用（PRD-05）。

### 4-5. ビジネスモデル

> 「本サービスは法人・個人事業主などの事業者間取引を対象とする。ゲスト購入は提供しない。」（依頼者, 2026-08-16）

→ コンサル所感: 収益源は SaaS 利用料ではなく、卸売取引そのものの商品マージン（小売希望価格と卸価格の差）。BIZ-03 は「サブスクプラン」ではなく「卸取引条件（価格・支払条件・送料）」として定義する。

### 4-6. ロール設計

> 「会社・取引先情報と、ログインユーザー情報は分けて管理する。会社：契約および取引の主体。ユーザー：会社に所属してシステムを操作する担当者。将来的に、一つの会社へ複数ユーザーを所属させられる構造とする。」（依頼者, 2026-08-16）

→ コンサル所感: 取引先会社（Organization 相当）と所属ユーザー（Membership 相当）を分けて管理したいという要望自体は明確。ただし本リポジトリの標準テンプレートは、`apps/public` 側の会員（Member）をロール階層・組織階層を持たない単一種別として扱うのが既定（DEV-01 §1「Permission」）。本案件は「1 取引先会社に複数ユーザーが将来所属し得る」という点で標準からの拡張が必要であり、テンプレ標準からの逸脱として PRD-01（ドメインモデル）で設計し GOV-01 に決定として記録する。ロール数自体は最小: 運営側は「admin」相当の 1 ロールのみ、取引先側も現時点では区別のない「取引先ユーザー」の 1 ロールのみが顧客発言の全て。取引先側の管理者権限（会社内で権限差を設けるか）は未言及のため `[Open: TBD-05 GOV-02、影響: PRD-01 §1-2 / DEV-02 §2]` として管理する。

### 4-7. コンテンツの更新主体

顧客発言としての記録はない（当初の仕様検討では「誰が更新するか」を論点として扱っていなかった）。以下は 2026-09-09 に PdM が確定させた方針である。

→ コンサル所感: 当初の設計では全コンテンツを D1 テーブルとして扱っていたが、公開コンテンツには運営が管理画面から更新するものと開発者がリポジトリで更新するものが混在しており、後者に D1 とその管理画面を用意するのは過剰である。「クライアントが更新するもの → D1 + 管理画面 / 開発者が更新するもの → Markdown・定数・ページ直書き」で置き場所を決める（DEV-06 §1-1）。

**2026-09-16 に更新主体を再確認した結果、公開コンテンツはすべて「開発者が更新する」に確定した**（商品の改訂は半年に 1 回程度で、実施するのは開発者）。したがって D1 + 管理画面に残るコンテンツは 1 つも無い（GOV-01 D-017・D-018）。

| コンテンツ | 置き場所 | 更新主体 |
| --- | --- | --- |
| 商品カタログ（商品・メーカー・ブランド）| Content Collections（`packages/content`）| 開発者 |
| 取引先別の個別卸価格 | Content Collections（`organizations.org_code` を参照）| 開発者 |
| お知らせ | Content Collections | 開発者 |
| 商品選び診断のルール（質問・選択肢・推奨商品のマッピング）| Content Collections | 開発者 |
| 商品画像 | 静的アセット（`apps/public/src/assets/img/`）| 開発者 |
| 商品カテゴリー・気になる点の分類、よくある質問（FAQ）、送料・税率・支払方法、お問い合わせ種別 | TypeScript 定数 | 開発者 |
| 利用規約・プライバシーポリシー・特定商取引法に基づく表示 | ページ直書き | 開発者（文面は法務レビュー） |

> **帰結**: 商品カタログ系 8 テーブルと `news` が不要になり、管理画面は 25 → 12 画面に減った（PRD-04 §3-2）。同時に**運営はお知らせも自分では出せなくなる** — 臨時休業や出荷遅延の告知もデプロイを伴う。これは確認のうえで選んだ構成であり、運用が回らない場合の戻し方は GOV-01 D-018 の再評価条件にある（GOV-02 TBD-20 で追跡）。
>
> 診断ルールを Content Collections に置いた結果、当初検討していた診断系 4 テーブル（`diagnosis_sets` / `diagnosis_questions` / `diagnosis_choices` / `diagnosis_rules`）は不要になった（これらには対応する管理画面が無く、テーブルはあるのに更新手段がない状態だった）。法務ページを直書きにした結果、同意した規約バージョンを記録する先が必要になり、`applications.agreed_terms_version` を追加した（DEV-07 §5-1）。
